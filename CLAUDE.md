# audio-queue

iOS app ("cue") + Node/Express backend. A saved link resolves to exactly one of
two things: a **podcast episode** (`audioURL` set — the app plays it) or a
**web item** (`audioURL` null — the app opens it in a web view).

## Layout

- `backend/` — Express 4 + Prisma 5 + Postgres, deployed on Railway
- `iOS/` — SwiftUI, project generated by XcodeGen from `iOS/project.yml`

## Deployment

| | |
|---|---|
| Railway project | `pretty-wisdom` |
| Service | `audio-queue` (plus a `Postgres` service) |
| Environment | `production` |
| URL | https://audio-queue-production.up.railway.app |
| Deploys from | `main`, automatically on merge |

```bash
railway link -p pretty-wisdom -e production -s audio-queue
```

Then `railway logs`, `railway status`, `railway deployment list`.
`railway run -s audio-queue <cmd>` runs a command **locally** with production
env vars injected — useful for exercising real code against the real API key,
but note it is *not* on Railway's network, so `postgres.railway.internal` is
unreachable and any database call fails.

## Verifying a resolve end-to-end

Do not ask a human what their queue shows. Run this — it creates a throwaway
anonymous account, adds the URLs, prints exactly what resolution produced, and
deletes the account afterwards. It never touches a real user's queue.

```bash
node backend/scripts/verify-resolve.mjs --debug "https://www.youtube.com/watch?v=..."
```

A title equal to the URL itself means resolution failed.

`--debug` additionally calls `GET /api/debug/resolve`, which reports what the
**server** sees for a page — the only way to observe behaviour specific to
Railway's IP, such as a consent wall or bot check that a laptop never gets.
That endpoint is inert unless `DEBUG_RESOLVE=1` is set on the service.

## Gotchas

- **Express 4 does not catch async handler rejections.** Every route is async
  and hits the database, so an unwrapped handler turns one failed query into an
  unhandledRejection. Wrap every async route in `asyncHandler`. This once took
  production down for ~36 hours: the process exited, `railway.toml` sets
  `restartPolicyMaxRetries = 3`, and after three deaths Railway stopped
  restarting — a silent 502 on every endpoint, with a `SUCCESS` deployment and
  clean boot logs.
- **Resolution runs once, at add time,** and the result is stored. Items added
  while the resolver was broken never repair themselves — delete and re-add.
- **`LISTEN_NOTES_API_KEY`** is the current metadata provider. Any
  `PODCAST_INDEX_*` variables are dead leftovers. Without the key,
  `findEpisode` returns null immediately and *every* link becomes a web item.
- **Listen Notes `q` is the only required parameter**, and a blank one is a 400.
  `cleanTitle` can empty a title (`"- YouTube"` → `""`), so guard before calling.
- **Page metadata lives in `<head>`, which can be huge** — YouTube's is >700 KB.
  Cut on `</head>`, never on a fixed byte count.
- **Podcast YouTube channels post clips as well as episodes.** A clip has no
  corresponding podcast episode; resolving it to a web item is correct.
- **Prisma is v5, not v7+.** v7 removed `url` from the datasource block.
- iOS: run `xcodegen generate` in `iOS/` after editing `project.yml`.
  `Info.plist` is generated from it — edit `project.yml`, not the plist.
